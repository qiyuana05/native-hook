## 1. 从一个现象开始

这台车机（长安启源 A05，Android 9）装一个不在它名单里的应用：

- 有时候连装都不让你装；
- 有时候装进去了，几秒钟后又被安全服务卸掉，提示「检测到非授权应用安装，已终止其运行，并卸载成功」。

常规思路是找白名单、改包名、或者签一个它认识的证书——本质都是**伪造身份**。

这个项目走了另一条路：**不改系统，不刷分区，也不碰安装包**，只在目标进程运行时，
往它的内存里放一段自己的代码，把「检查」那个函数的入口换掉。

这段代码 407 KB。它替换掉的旧方案叫 Frida，光注入器一个文件 51 MB。

为什么能做到？分三层回答：**换成什么**（第 2–5 节）、**怎么进去**（第 6 节）、
**进去之后怎么一直在**（第 11 节）。

## 2. Hook 到底在改什么

Hook 做的事很朴素：程序本来要执行 A，你在中间插一段，让它执行 B，或者执行完 B 再回到 A。

### 2.1 改结果，还是改入口

| 做法 | 手段 | 局限 |
|---|---|---|
| **改返回值** | 让某个检查函数返回 `true` 而不是 `false` | 只对「你够得着的那一个调用点」有效；换入口、换线程、换进程就不灵；检查逻辑本身还在 |
| **改入口** | 让所有调用者走到这个函数时，先走到我的代码 | 不需要知道有多少调用方、从哪调用 |

改入口更彻底，因为它把「谁调用了这个检查」这个问题变成了「这个检查本身是谁」。
不需要枚举调用点，一次替换覆盖全部路径。

### 2.2 inline hook

最直接的改入口方式叫 **inline hook**：把目标函数开头的几条指令改成一条跳转，
跳到我的函数；被覆盖掉的那几条原指令搬到旁边一块内存里，执行完再跳回原函数的下一条。

```
目标函数:  [原指令1][原指令2][原指令3][原指令4] ...   ← 开头被写成 jmp 我的函数
                 ↓ 搬到
trampoline: [原指令1][原指令2][原指令3][jmp 原函数+12]   ← 跳板
```

听上去很简单：把入口地址一改不就完了？在普通 C 程序里确实可以这么理解。
但在 Android 上，中间隔着一层东西。

## 3. 为什么 Android 上不能直接改地址

### 3.1 dex 不是机器码

Android 应用代码写在 dex 里，是字节码。真正把它跑起来的是 **ART**（Android Runtime）：

- 解释执行；
- 把热点方法 JIT 编译成机器码；
- 也可能 AOT 预编译、甚至把方法**内联**进调用方。

这意味着「改一个函数入口」这个动作，在 ART 上会遇到一个麻烦：**方法可能已经不存在一个
稳定的入口了**——它被编译过、被内联过，改指针不一定生效。

### 3.2 ArtMethod

对每一个 Java 方法，ART 在内存里维护一个结构体 `ArtMethod`。
可以把它想成这个方法的**工位档案**：

| 字段 | 含义 |
|---|---|
| declaring class | 属于哪个类 |
| access flags | 是不是 static / native / abstract |
| dex method index | 对应 dex 里哪一段代码 |
| **entry point**（`data_` 或 `ptr_sized_fields_`） | **入口地址：调用最后跳到这里** |

一次 Java 调用走到最后，就是跳到这个入口。

所以 hook 一个 Java 方法，本质是**把这个入口换成我的入口**。

**但这里有个坑：不能随便换成一个 C 函数。**

调用方是按 Java 的 ABI 布置寄存器/栈的：

- 实例方法的第一个参数是 `this`，后面才是各参数；
- 基本类型直接放在寄存器里，对象是引用；
- 返回值放哪也有约定（ARM64 上一般在 `x0` / `v0`）；
- 更进一步，ART 可能走「快速编译代码入口」而非通用入口。

你换上去的函数签名必须一模一样，否则参数一解就是错的，直接崩。

> **所以真正的问题不是怎么改地址，而是改成一个什么地址。** 这就是 LSPlant 要解决的。

## 4. LSPlant：生成一个签名兼容的替身

[LSPlant](https://github.com/LSPosed/LSPlant) 是 LSPosed 团队开源的 ART hook 库。
它不要求你写一个签名一模一样的 C 函数，而是在**运行时生成一个替身类**：

1. 替身方法的**签名和目标方法完全一致**——所以调用方的参数能被原样接住；
2. 替身把参数**装箱**进一个 `Object[]`，调用你提供的回调；
3. 你的回调签名是固定的：`(Object[] args, Object backup) -> Object`。

```
Java 调用 ──→ ArtMethod.entry ──→ 替身方法（签名生成，与原方法一致）
                                     │
                                     ├─ 装箱参数 → Hooker.callback(args, backup)
                                     │                  │
                                     │                  ├─ return true   放行
                                     │                  ├─ return false  拒绝
                                     │                  └─ call backup   走原逻辑
                                     └─ 回调返回值 → 装箱解箱 → 返回给调用方
```

### 4.1 backup 是什么

LSPlant 在 hook 时返回一个 **backup 方法**，它指向原来的入口。你在回调里调用 backup，
等于调用原方法。

这意味着你不是在破坏原逻辑，而是在**接管**它：可以放行、可以拒绝，也可以先做点别的
再原样放行。本项目的四个模块（安装门、卸载门、状态栏、投屏全屏）本质上都是这一件事的
不同用法。

`backup` 在回调里怎么调，见 [`payload/src/main.cpp` 的 `CallBackup()`](../payload/src/main.cpp#L195)。
这里有个坑，见[第 12.1 节](#121-backup-的静态判断错一次-闪退一片)。

### 4.2 去优化

方法可能已经被编译、被内联，光改入口不一定生效。所以 hook 之后还要**去优化**
（deoptimize），让旧的编译代码失效，回退到能走新入口的状态。

而 LSPlant 自己也得在 ART 内部的函数上做 inline hook 才能把链路接起来。
这时候它需要一个更底层的东西，把跳转真正写进指令里——那就是 Dobby。

## 5. Dobby：把跳转真正写进机器码

[Dobby](https://github.com/jmpews/Dobby) 是一个轻量 inline hook 框架，支持 ARM / ARM64 / x86。
它做的事一句话：**在目标函数开头写一条跳转，跳到我的函数；把被覆盖的原指令搬到
trampoline；执行完再跳回原函数的下一条。**

### 5.1 ARM64 上的跳转距离问题

一条 ARM64 的 `B` 指令只能跳 ±128 MB。而目标函数和你的函数可能隔得很远。
所以实际写进去的往往不是一条 `B`，而是一小段：

```asm
ldr x16, #8        ; 把下面 8 字节的地址装进 x16
br  x16            ; 跳过去
.quad <目标地址>    ; 64 位绝对地址
```

### 5.2 必须处理的四件事

| 问题 | 为什么麻烦 |
|---|---|
| **指令边界** | 只能整条指令替换，不能把一条 4 字节指令切成两半；要算清楚覆盖了几条 |
| **PC 相对寻址** | 被搬走的指令里可能有 `adr` / `ldr literal`，搬走之后相对偏移就错了，要重定位 |
| **指令缓存刷新** | 改完内存必须刷 I-cache，否则 CPU 还执行旧指令 |
| **多线程并发** | 最麻烦的：你改的时候，**别的线程可能正执行到这段代码中间** |

### 5.3 在本项目里怎么接进 LSPlant

LSPlant 不直接依赖 Dobby，而是让你把「inline hook 怎么做」通过回调注入进去。
[`payload/src/main.cpp`](../payload/src/main.cpp#L571) 里就是这么接的：

```cpp
lsplant::InitInfo info{
    .inline_hooker = [](void* target, void* hooker) -> void* {
      void* backup = nullptr;
      if (DobbyHook(target, hooker, &backup) != RT_SUCCESS) return nullptr;
      return backup;                      // Dobby 返回的 trampoline 就是 backup
    },
    .inline_unhooker = [](void* func) { return DobbyDestroy(func) == RT_SUCCESS; },
    .art_symbol_resolver = [&art](std::string_view s) { return art.Resolve(s); },
    .art_symbol_prefix_resolver = [&art](std::string_view p) { return art.ResolvePrefix(p); },
    .generated_class_name = "LSPHooker_NH_",
};
```

`art_symbol_resolver` 是关键：LSPlant 需要知道 ART 内部一堆函数在哪（怎么从反射对象拿
`ArtMethod`、怎么调用、怎么去优化）。这个 resolver 从 `libart.so` 的符号表里查。
符号表在不在，是[第 7 节](#7-三个前提)的第三个前提。

## 6. 怎么进到别人的进程

到这里讲的都还是「进去以后怎么做」。更难的问题是**怎么进去**。

Android 的进程是隔离的。一个普通应用别说改 `system_server` 的内存，
连它的 `/proc/<pid>/` 都不一定读得到。

### 6.1 第一步：权限

这台车机上有一条厂商私有通道：系统应用 `com.incall.spm` 里的 `DMService`，接受特定格式的
消息（本项目用的消息类型是 `DM01`），由系统侧的 daemon 以 **root** 身份执行命令。
不需要 Magisk，不需要 LSPosed，也不需要解锁 bootloader。客户端实现在
[`apk/src/com/changan/nativehook/DmClient.java`](../apk/src/com/changan/nativehook/DmClient.java)。

拿到 root 之后，SELinux 仍然处于 **Permissive**（只记日志、不拦截）。

> ⚠️ **这一段是本项目唯一依赖厂商缺陷的部分**，也是最不应该被复用到他人设备上的部分。
> 它不是 hook 技术的必要条件——任何 root 来源（Magisk、adb root、工程模式）都能提供同样的能力。
> 之所以保留，是因为「先有 root」这个前置条件必须讲清楚，否则后面全是空中楼阁。

### 6.2 第二步：让目标进程停下来

Linux 有个系统调用叫 `ptrace`，调试器用它下断点、看寄存器、改内存。
我们对 `system_server` 做的就是这件事：

```
PTRACE_ATTACH → waitpid → 目标进程停止，PTRACE_GETREGSET 保存全部寄存器
```

保存的寄存器等会儿要原样还回去——目标是让这个进程「只卡了一下」，看不出被改过。

### 6.3 第三步：借它的手调 dlopen

这是最像魔术的一步。我们想让目标进程**自己**调用 `dlopen`，加载我们的库。怎么做？

> 不能让注入器代替它 `dlopen`——库必须加载进**目标进程自己的地址空间**才算数。

具体做法是「布一个局」，让目标进程从 `dlopen` 的入口开始执行：

```c
// injector/nhinject.c:292  remote_dlopen()
write_mem(pid, scratch, lib_path, strlen(lib_path) + 1);   // 1. 路径写到它的栈上
struct arm64_regs regs = *saved;
regs.regs[0]  = scratch;                                 // 2. x0 = 路径
regs.regs[1]  = RTLD_NOW | RTLD_GLOBAL;                  //    x1 = 加载标志
regs.pc       = dlopen_addr;                             // 3. PC = dlopen 地址
regs.regs[30] = brk_addr;                                // 4. LR = libc 里的 brk #0 断点
set_regs(pid, &regs);
ptrace(PTRACE_CONT, pid, NULL, NULL);                    // 5. 让它跑
```

然后：

1. 目标进程「以为自己」在正常执行：从 `dlopen` 进去，加载库，**执行它的构造函数**；
2. 返回时顺着 `LR` 跳到 `brk #0` 指令，触发 `SIGTRAP`，**时间再次暂停**；
3. 读 `x0` 就拿到了 `dlopen` 的返回值（handle）；
4. 把保存的寄存器**原样写回**，`PTRACE_DETACH`。

从外面看，这个进程只是短暂卡了一下。整个注入器编译出来约 14 KB。

`brk_addr` 不是猜的：注入器先从 `/system/lib64/libc.so` 里定位 `brk` 指令的位置
（`elf_find_symbol`），`dlopen_addr` 同理从 `libdl.so` 里找。所以注入器自己也要会解析 ELF。

### 6.4 重复注入保护

`nhinject` 在 attach 之前会先读 `/proc/<pid>/maps`，如果里面已经有 `libnhpayload.so`，
**直接跳过**。

这不是优化，是保命：对一个已经加载过 payload 的进程再 `dlopen` 一次，LSPlant 会
二次 `Init`，轻则 hook 全失效，重则把 `system_server` 打软重启，车机黑屏重启。
这个坑真踩过（[第 12.2 节](#122-连点两次开启-hook-车机软重启)）。

## 7. 三个前提

拿到 root 之后，还有三个前提必须**同时**成立，这套方案才work。
缺一个都不行，所以这不是一个通用方法。

| # | 前提 | 为什么必需 | 怎么自查 |
|---|---|---|---|
| 1 | 链接器允许从 `/data` 加载 | Android 7+ 有 linker namespace，能加载哪些路径是白名单写死的 | `grep permitted.paths /system/etc/ld.config.*.txt` |
| 2 | SELinux 是 Permissive | 若为 Enforcing，`system_server` 执行 `/data` 里的文件会被直接拒绝 | `getenforce` |
| 3 | `libart.so` 符号表完整 | LSPlant 靠符号名解析 ART 内部函数；没有符号就只能硬编码偏移，换版本即废 | `nm -D /system/lib64/libart.so \| wc -l` |

本机实测：`namespace.default.permitted.paths += /data`、`getenforce` → `Permissive`、
`libart` 约 12,171 个导出符号。

```
        ┌──────────────────────┐
        │   hook 能成立         │
        └──────────┬───────────┘
       ┌───────────┼───────────┐
  /data 可加载   Permissive   libart 符号完整
     (链接器)    (访问控制)      (LSPlant 找函数)
```

**这不是「Android 的一个通用后门」，是这台车、这个固件版本上的一个特定组合。**
换车、换版本、一次 OTA，任意一根柱子倒了，整套东西就失效。

## 8. 进场之后：初始化流水线

库被加载进来，第一件事**不是** hook。

### 8.1 构造函数只起一个线程

```cpp
// payload/src/main.cpp:638 —— 构造函数里只做一件事
__attribute__((constructor)) static void OnPayloadLoad() {
  LOGI("runtime constructor pid=%d", getpid());
  pthread_t thread;
  if (pthread_create(&thread, nullptr, InitThread, nullptr) == 0) {
    pthread_detach(thread);      // 不等它，构造函数立刻返回
  } else {
    LOGE("pthread_create failed");
  }
}
```

为什么？因为初始化要加载模块、调 JNI、解析符号。这些放在构造函数里会把 `dlopen`
**卡住**，而注入器正等着 `dlopen` 返回（[6.3](#63-第三步借它的手调-dlopen)）。
构造函数越快返回越好。

### 8.2 InitPayload 的六步

线程里依次做：

| 步 | 做什么 | 代码 |
|---|---|---|
| 1 | 找到进程里已有的 JavaVM | `JNI_GetCreatedJavaVMs`，[`main.cpp:540`](../payload/src/main.cpp#L540) |
| 2 | attach 上去，拿到 `JNIEnv` | `AttachCurrentThread`，[`main.cpp:551`](../payload/src/main.cpp#L551) |
| 3 | 打开 `libart.so`，建符号解析器 | `ElfSymbolResolver art(kArtPath)`，[`main.cpp:563`](../payload/src/main.cpp#L563) |
| 4 | 初始化 LSPlant，把 Dobby 和 resolver 交给它 | `lsplant::Init(env, info)`，[`main.cpp:596`](../payload/src/main.cpp#L596) |
| 5 | 加载内嵌的 Hooker DEX，注册 native 回调 | `InMemoryDexClassLoader` + `RegisterNatives`，[`main.cpp:273`](../payload/src/main.cpp#L273) |
| 6 | 扫描 `modules/` 目录，按 scope 加载模块 | `LoadModules()` |

### 8.3 为什么要内嵌一个 dex

Hooker 必须是一个**Java 类**——LSPlant 的回调是 Java 方法，不是 C 函数。
但我们的 payload 是个 `.so`，没法带 `classes.dex`。

做法是把 `Hooker.class` 编译成 dex 后转成 C 数组内嵌进 payload
（`payload/hooker/build-dex.sh` 生成 `payload/src/hooker_dex.h`），
运行时用 `InMemoryDexClassLoader` 直接从一个 `ByteBuffer` 加载——
不落盘，不依赖文件系统。

这个 dex 只有几百字节，是整个「407 KB」里最容易被忽略的一小块。

## 9. 模块化：一个运行时，五个进程

### 9.1 为什么拆模块

最早所有功能都写在 `main.cpp` 里。问题是：改一个功能要重新编译整个 payload，
而 payload 一换，**所有五个进程都得重启才能用上**。

所以现在的边界是：

- `libnhpayload.so` 是**固定运行时**：LSPlant 初始化、回调分发、模块加载、状态文件；
- 具体功能全在 `modules/*.so` 里，模块自己声明在哪个进程生效。

新增功能不改运行时，只加模块。ABI 只有 34 行，见
[`payload/include/nhook_module.h`](../payload/include/nhook_module.h)：

```c
typedef struct nhook_api {
  uint32_t version;                       // ABI 版本
  const char* (*process_name)(void);
  const char* (*config)(const char* key);
  void (*log)(const char* message);
  int  (*hook_method)(JNIEnv*, const char* cls, const char* m,
                      const char* sig, nhook_callback, void* user);
  int  (*hook_all)(JNIEnv*, const char* cls, const char* m, nhook_callback, void*);
  jobject (*call_backup)(JNIEnv*, jobject backup, jobjectArray args);
} nhook_api;
```

模块导出三个符号：

| 符号 | 作用 |
|---|---|
| `nhook_module_name` | 模块名，写进日志和状态文件 |
| `nhook_module_scope(process)` | 返回非 0 表示「我要在这个进程生效」，类似 LSPosed 的 scope |
| `nhook_module_init(env, api)` | 真正干活：调 `api->hook_method(...)` |

### 9.2 五个进程，各取所需

| 进程 | 模块 | 接管什么 |
|---|---|---|
| `system_server` | `uninstall_guard` | 安装门 + 卸载门 + 安全服务拦截 |
| `com.vecentek.decoreapp` | `uninstall_guard` | 同一份代码，安全服务进程 |
| `com.android.systemui` | `statusbar_touch` | 状态栏触摸 / 显示 |
| `com.iflytek.autofly.voicecoreservice` | `hide_presentation` | 副屏 Presentation 窗口 |
| `com.wt.phonelink` | `iccoa_fullscreen` | 投屏分辨率与 dpi |

一个运行时，五个进程，各取所需。写新模块的完整规范见 [MODULE-STANDARD.md](MODULE-STANDARD.md)。

### 9.3 配置与状态

- 配置：`/data/system/uninstall-hook-native.cfg`，`key=value` 行格式，模块用
  `api->config("iccoa")` 读；
- 状态：每个进程一份 `/data/system/nativehook-<process>.status`，
  内容是 `ok=1 / pid=... / hooks=5`，保活巡检读它判断存活。

状态文件这条设计带来一个很隐蔽的坑，见[第 12.4 节](#124-status-文件被别的-uid-以-0600-建过)。

## 10. 没有 ART 的进程：GOT 覆盖

不是所有进程都有 JavaVM。车机上负责后摄循环录像的 `evsserver` 是**纯 native** 进程，
LSPlant 那一套完全用不上——没有 `ArtMethod`，没有 Java 方法，hook 谁？

这时候用另一种 hook：**GOT 覆盖**。

ELF 程序调用外部函数（比如 `ioctl`、`open`）要经过一张跳转表 `GOT`（Global Offset Table），
表里存的是解析后的函数地址。**把表项里的地址换掉，调用就走到我的函数**：

```
GOT:  [ ioctl  → 0x7f...a100 ]   ← 改成 0x7f...b200（我的函数）
      [ open   → 0x7f...a240 ]
      [ ...                       ]
```

重定位类型是 `R_AARCH64_JUMP_SLOT`。不需要改指令，不需要 ART，只需要能写那段内存。

**同一个「hook」，在不同进程里可以是完全不同的技术。** 它不是一把万能钥匙，
是一组工具，得知道什么时候用哪一把。

> `evsserver` 那条路不在本仓库（它跑在纯 native 进程，用不上 LSPlant/Dobby 这套依赖），
> 代码在独立的 `evs-dvr` 项目。本仓库只在配置里留了 `evs_dvr` 开关和拉起逻辑。

## 11. 保活：hook 是一瞬间，保活是全部

Hook 有个天生的弱点：**只活在内存里**。

目标进程一重启，写进去的东西就没了；车机一熄火，全都没了。
所以真正的工作量不在 hook 成功那一下，而在怎么让它一直在。

### 11.1 三层结构

```
┌─────────────────────────────────────────────┐
│ 第一层：空壳无障碍服务（系统长期 bind 本进程）    │
│  ┌───────────────────────────────────────┐  │
│  │ 第二层：root 侧 nhkeepd（15s 巡检）     │  │
│  │  ┌─────────────────────────────────┐  │  │
│  │  │ 第三层：App 内 KeepAliveService  │  │  │
│  │  └─────────────────────────────────┘  │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

| 层 | 实现 | 作用 |
|---|---|---|
| 一 | `KeepAliveAccessibilityService` | `capabilities=0`、不读窗口内容、不接管手势。唯一作用是让系统长期 bind 本进程，被杀/覆盖安装后自动重连 |
| 二 | `daemon/nhkeepd.cpp` | root 侧常驻，`setsid` 拉起，**不随 App 退出**。每 15 秒扫一遍进程列表 |
| 三 | `KeepAliveService` | App 活着时兜底；检测到 `nhkeepd` 心跳就**主动让位**，避免两边同时注入 |

第三层的「让位」很关键：两层巡检如果同时决定注入，就会撞上重复 `dlopen`，
后果见[第 6.4 节](#64-重复注入保护)。所以第二层启动后会写一个心跳文件
`nhkeepd.hb`（15 秒更新一次），第三层看到心跳就只观察不动作。

### 11.2 nhkeepd 的一轮巡检

```
每 15 秒：
  for 每个配置里的目标进程:
      读 /proc/<pid>/maps
      含 libnhpayload.so ?
        ├─ 是 → 跳过（已在）
        └─ 否 → fork/exec nhinject <pid>
  更新 nhkeepd.hb
```

判断依据是 `/proc/<pid>/maps`，不是状态文件——状态文件可能因为各种原因 stale，
而 `maps` 是内核给的真相。

### 11.3 实测

- 开机约 **13 秒**完成 5 个进程注入；
- `kill -9` 掉 SystemUI 或投屏进程，**15 秒内**补回来；
- App 被 force-stop，注入**不受影响**（因为第二层在 root 侧）。

## 12. 踩过的坑

这一节是这份文档里最有价值的部分。上面所有设计决策，基本都是被这些坑推出来的。

### 12.1 backup 的静态判断：错一次，闪退一片

**现象**：进投屏必闪退，日志 `dpi must be between 120 and 640`；下拉状态栏 SystemUI 崩。

**原因**：`CallBackup()` 里要区分「原方法是静态还是实例」来决定怎么调：

```cpp
// 错误写法
bool is_static = Modifier.isStatic(backup.getModifiers());
```

`backup` 是 LSPlant **运行时生成**的方法。生成时它的 dex flags 是一套，
而 `DoHook` 会把原方法 `ArtMethod` 的内容（含 access flags）整体拷进 backup——是另一套。
所以 `backup.getModifiers()` 不可靠。

后果：实例方法被当成静态，`this` 被丢掉，原方法**根本没执行**。
`initDisplayMetrics` 没执行 → `dpi` 变成 0 → `setDpi` 抛错 → 闪退。
更隐蔽的是 `WindowManagerGlobal.addView` 没执行，界面看着正常，一点就崩。

**正确写法**：在 hook 时**记下目标方法本身**是不是静态，存在 map 里，
`CallBackup` 时按目标方法判断：

```cpp
// payload/src/main.cpp:379 附近
g_backup_static[backup_id] = target_static;   // target_static 来自目标方法
```

**教训**：这种 bug 看日志看不出来。日志里只有「dpi 超范围」，
你得一行一行对到「为什么 dpi 是 0」，再对到「为什么原方法没执行」。
**运行时生成的东西，它的元数据不要信。**

### 12.2 连点两次「开启 Hook」，车机软重启

**现象**：快速点两次按钮，车机黑屏重启。

**原因**：第二次点击又跑了一遍注入。`dlopen` 不会因为「已经加载过」就跳过——
它对一个新的 soname 路径会再加载一份，构造函数再跑一次，LSPlant 二次 `Init`。
ART 被初始化两次，`system_server` 直接软重启。

**修法**：注入前看 `/proc/<pid>/maps`，有 `libnhpayload.so` 就跳过
（[6.4](#64-重复注入保护)）。同时三层保活里的「让位」机制也是为这个加的。

### 12.3 `libc++_shared.so` 缺失

payload 早期用默认的 `-static-libstdc++` 之外的方式编译，产物依赖 `libc++_shared.so`。
而目标进程是系统进程，它的 linker namespace 里**没有** `libc++_shared.so`，
`dlopen` 直接失败。

**修法**：payload 用 `-static-libstdc++` 把 C++ 运行库打进去；
模块更狠，直接 `-nostdlib++` —— **模块只依赖 libc / libdl / libm**。

### 12.4 status 文件被别的 uid 以 0600 建过

**现象**：注入明明成功了，界面还是弹「注入失败」。

**原因**：状态文件 `/data/system/nativehook-<pkg>.status` 曾经被另一个 uid
以 `0600` 权限创建过。目标进程（比如 `system_server`）写不进去，
于是界面读到的是旧内容或空内容。

**修法**：写状态文件前先 `chmod`，并且用「写临时文件 + rename」避免半截内容；
App 侧读不到就当 stale 处理，不等它。

### 12.5 开机后一分多钟才注入

**现象**：开机后要等 60 多秒才注入完成。

**原因**：`ensureServices()` 在等 DM 通道的回调。开机早期 DMService 还没就绪，
回调要拖到 60 秒超时——但脚本事后确实执行成功了。

**修法**：不再等回调，按「脚本已下发」就继续；把结果轮次的判断改成看状态文件。
开机注入从 74 秒压到 13 秒。

### 12.6 `GetStaticFieldID` 找一个实例字段

**现状：已知问题，未修。**

`statusbar_touch` / `hide_presentation` 用 `GetStaticFieldID` 找
`WindowManagerGlobal.mViews`，但它是**实例字段**。结果每 3 秒在日志里刷
`mViews missing`，sweep 逻辑实际没生效。

功能上没崩（因为主路径不走 sweep），但这是一处真实的错误，留在[README 已知问题](../README.md#已知问题)里。

## 13. 代价与边界

### 13.1 前提会变

依赖 Permissive、依赖 `/data` 可加载、依赖符号表完整（[第 7 节](#7-三个前提)）。
换一台车、换一个系统版本、甚至一次 OTA，都可能失效。

### 13.2 版本适配成本

`ArtMethod` 的内存布局每个 Android 版本都可能不一样。LSPlant 官方声明支持
Android 5–17（上游说法，非本车实测），但**每个 ROM 仍然要实测**。
本项目只在 Android 9 / arm64 / MT8666 上验证过。

### 13.3 许可证

LSPlant 是 **LGPL-3.0**，Dobby 是 **Apache-2.0**。自己研究没问题，
真要分发产物得看清条款——本项目对 LSPlant 是动态链接、未改源码，
详见 [THIRD-PARTY.md](../THIRD-PARTY.md)。

### 13.4 最后一句

**这套东西只改内存，不写系统分区，重启就恢复。**

它适合研究你自己的车，不适合做任何未经授权的事。
在他人车辆上使用它属于未授权访问，并且可能影响车辆功能与安全。
